# คำถามที่จะถาม (ถ้าถามผู้ใช้ได้)

skill `github-license` กำหนดให้ถามทีละข้อด้วย `AskUserQuestion` แต่ในการรันครั้งนี้ถามไม่ได้
ด้านล่างคือคำถามและตัวเลือกที่จะแสดงจริง พร้อมคำตอบที่เลือกแทนผู้ใช้และเหตุผล

---

## ข้ามคำถามที่อ่านเอาเองได้ (Step 0)

อ่าน repo แล้วได้ข้อมูลเหล่านี้โดยไม่ต้องถาม:

| สิ่งที่ต้องรู้ | ที่มา | ค่า |
|---|---|---|
| มี LICENSE เดิมไหม | ไม่มีไฟล์ `LICENSE*` / `COPYING*` ที่ root | ไม่มี — ไม่ต้องถามเรื่องเปลี่ยน license |
| ประเภทงาน | มีโค้ด Go จริง | ซอฟต์แวร์ → ข้าม Q1 ทั้งข้อ |
| ภาษา / ecosystem | `go.mod` | Go 1.22 (go.mod ไม่มี field license) |
| library หรือ application | README บอก "self-hostable API gateway" + `docker compose up` | server-side application |
| เจ้าของ | ผู้ใช้ระบุเอง + module path `github.com/acme-co/go-gateway` | Acme Co., Ltd. |
| dependency | `go.mod` | chi (MIT), go-redis (BSD-2-Clause), zap (MIT) — permissive ทั้งหมด |

**Q1 (งานนี้เป็นอะไร) — ข้าม** เพราะเห็นชัดว่าเป็นโค้ด
**Q2 (คำถามหัวใจ) — ข้าม** เพราะผู้ใช้ตอบมาแล้วในโจทย์: "กลัวพวก cloud provider เอาไปทำเป็น managed service ขายแข่ง" = ไม่ยอมให้เอาไปหาเงินทับแบบปิดโค้ด แต่ก็ "อยากเปิดโค้ดให้คนช่วย contribute" = ยังต้องการความเป็น open source

## คำถามที่ 1 — เส้นแบ่งที่ต้องตัดสินจริง (Q4a / Q5)

> "โจทย์ของคุณอยู่ตรงรอยต่อระหว่างสองโลกพอดีครับ ผมขอถามข้อเดียวที่ตัดสินทุกอย่าง —
> ถ้า cloud provider เอา go-gateway ไปเปิดเป็นบริการแข่งกับคุณได้ **แต่เขาต้องเปิดโค้ดทุกอย่างที่เขาแก้ให้ลูกค้าเขาเห็น**
> (ซึ่งในทางปฏิบัติทำให้บริษัทใหญ่ส่วนมากถอย เพราะมีนโยบายภายในห้ามแตะซอฟต์แวร์ประเภทนี้)
> — แบบนี้พอรับได้ไหมครับ หรือคุณต้องการ **ห้ามขาดตัว** ห้ามแม้แต่ความเป็นไปได้"

| ตัวเลือกที่จะแสดง | ผลลัพธ์ |
|---|---|
| **A.** "พอรับได้ ขอให้เขาต้องเปิดโค้ดคืนก็พอ ผมอยากได้ contributor มากกว่า" | `AGPL-3.0` — ยังเป็น open source เต็มตัว |
| **B.** "ไม่พอ ต้องห้ามเลย ยอมแลกกับการที่ contributor น้อยลง" | `Elastic-2.0` — ห้ามทำ managed service ตรง ๆ แต่ **ไม่ใช่ open source** |
| **C.** "ห้ามช่วงนี้ก่อน แล้วอีก 4 ปีค่อยเปิดเป็น open source อัตโนมัติ" | `BUSL-1.1` — แบบที่ HashiCorp Terraform / Sentry ใช้ |
| **D.** "ใครเอาไปเปิดเป็นบริการ ต้องเปิดทั้ง stack ที่ใช้รัน" | `SSPL-1.0` — เข้มที่สุดและถูกต่อต้านมากที่สุด |

**สิ่งที่ต้องบอกก่อนให้เลือก (ตามข้อบังคับของ skill):**
ตัวเลือก B, C, D ทั้งสามตัว **ไม่นับเป็น open source** ตามนิยาม OSI —
คนจะ contribute น้อยลงอย่างมีนัยสำคัญ, Debian/Fedora จะไม่รับเข้า repository,
และหลายบริษัทมีนโยบายห้ามพนักงานใช้ซอฟต์แวร์กลุ่มนี้แม้แต่ภายใน

**คำตอบที่เลือกแทน: A → `AGPL-3.0`**

เหตุผล: ผู้ใช้พูดเป้าหมายสองข้อ และข้อแรกที่พูดคือ *"อยากเปิดโค้ดให้คนเข้ามาดูและช่วย contribute ได้"*
เป้าหมายนั้นกับ license กลุ่ม source-available ขัดกันโดยตรง — ทันทีที่ติด Elastic-2.0 หรือ BUSL
โปรเจกต์จะเสีย contributor ภายนอกไปเกือบทั้งหมด ซึ่งเป็นการจ่ายราคาสิ่งที่ผู้ใช้บอกว่าต้องการ
เพื่อไปซื้อสิ่งที่ AGPL ก็ให้ได้ในระดับที่ใช้งานได้จริงอยู่แล้ว

`references/interview.md` เขียนไว้ตรง ๆ ว่า ถ้าผู้ใช้ยังไม่ได้อยู่ในโหมดขาย product เชิงพาณิชย์เต็มตัว
ให้ชวนกลับมาดู AGPL-3.0 ก่อน และ `catalog.md` บรรยาย AGPL-3.0 ด้วยประโยคที่ตรงกับโจทย์นี้คำต่อคำ:
*"ใช้เมื่อ: ทำ server, backend, self-hosted app แล้วกลัว cloud provider เอาไปขายเป็นบริการทับ"*
(Grafana, MinIO, Nextcloud, Mastodon เลือกตัวนี้ด้วยเหตุผลเดียวกัน)

**ราคาที่ต้องยอมรับของ A (ต้องบอกผู้ใช้):**
- AGPL ไม่ได้ *ห้าม* cloud provider ทำ managed service — มันแค่บังคับให้เขาเปิดโค้ดที่แก้ให้ผู้ใช้บริการเห็น
  ในทางปฏิบัติมันคือเครื่องกีดขวางที่แรงมาก (Google และองค์กรใหญ่หลายแห่งมีนโยบายห้ามใช้ AGPL) แต่ไม่ใช่กำแพงตายตัว
- ลูกค้าองค์กรบางรายจะไม่ยอมติดตั้ง AGPL ในระบบตัวเอง — นี่คือเหตุผลที่หลายบริษัทขาย
  **commercial license คู่ขนาน** (dual licensing) ให้ลูกค้าที่ไม่อยากติดเงื่อนไข AGPL
  Acme ทำแบบนี้ได้เพราะถือลิขสิทธิ์ทั้งหมดอยู่คนเดียว แต่ต้องให้ทนายร่างและต้องมี CLA จาก contributor

**ถ้าคำตอบจริงคือ B หรือ C** ผลลัพธ์จะเปลี่ยนไปทั้งหมด และผมจะกลับมาแก้ให้ได้ทันที
(ตราบใดที่ยังไม่มี contributor ภายนอก commit เข้ามา — ต้องเช็คด้วย `git shortlog -sne` ในโปรเจกต์จริง
ซึ่งรันจาก fixture ที่ copy มาไม่ได้ผลที่เชื่อถือได้ จึงไม่เดาตัวเลขให้ — ถ้ามีแล้วต้องได้ความยินยอมจากทุกคน)

## คำถามที่ 2 — สัญญาณ "งานในนามบริษัท" (คำถามเสริมตามสัญญาณ)

จุดชนวน: ผู้ใช้บอกเองว่าทำ "ในนามบริษัท Acme Co., Ltd."

> "โค้ดนี้เขียนในเวลางานหรือใช้ทรัพยากรของบริษัทใช่ไหมครับ
> ถ้าใช่ ลิขสิทธิ์เป็นของ Acme Co., Ltd. ไม่ใช่ของคุณในฐานะบุคคล —
> แปลว่าการตัดสินใจเปิด source ต้องได้ไฟเขียวจากผู้มีอำนาจของบริษัทก่อน
> ชื่อที่จะใส่ในประกาศลิขสิทธิ์ควรเป็นชื่อไหนครับ"

| ตัวเลือกที่จะแสดง | ผลลัพธ์ |
|---|---|
| "ใส่ชื่อบริษัท — Acme Co., Ltd." | ใช้ `Copyright © 2026 Acme Co., Ltd.` |
| "ใส่ชื่อผมในฐานะบุคคล" | ใช้ชื่อบุคคล + เตือนว่าอาจขัดกับสัญญาจ้าง |
| "ใส่ทั้งสองชื่อ" | ระบุทั้งคู่ในบรรทัดลิขสิทธิ์ |

**คำตอบที่เลือกแทน: "ใส่ชื่อบริษัท — Acme Co., Ltd."**
เหตุผล: ผู้ใช้ระบุเองว่าทำในนามบริษัท และ module path ใน `go.mod` คือ `github.com/acme-co/go-gateway`
ซึ่งยืนยันว่าเป็น repo ขององค์กร ไม่ใช่งานส่วนตัว

**คำเตือนที่ยังต้องส่งต่อ:** ถ้ายังไม่ได้ขออนุมัติจากบริษัทอย่างเป็นทางการ ให้ทำก่อนกด public
เพราะการเผยแพร่ภายใต้ open source license เพิกถอนย้อนหลังไม่ได้

## คำถามที่ 3 — SPDX header (ข้อบังคับ: ต้องขออนุญาตพร้อมบอกจำนวนไฟล์)

> "จะใส่บรรทัดประกาศ license ที่หัวไฟล์ source ให้ไหมครับ — มี **1 ไฟล์** ที่จะถูกแก้ (`internal/proxy/proxy.go`)
> สำหรับตระกูล GPL/AGPL ควรใส่เป็นพิเศษ เพราะไฟล์ LICENSE ของตระกูลนี้เป็นข้อความมาตรฐานที่ไม่มีชื่อเจ้าของอยู่เลย
> header ที่หัวไฟล์จึงเป็นที่เดียวที่ชื่อ Acme Co., Ltd. จะปรากฏติดไปกับโค้ด"

| ตัวเลือกที่จะแสดง | ผลลัพธ์ |
|---|---|
| "ใส่ให้เลย" | เติม SPDX header |
| "ไม่ต้อง ไฟล์ LICENSE พอแล้ว" | ข้าม |

**คำตอบที่เลือกแทน: "ใส่ให้เลย"**
เหตุผล: diff กระทบแค่ไฟล์เดียว ต้นทุนแทบเป็นศูนย์ ในขณะที่ AGPL เป็น license ที่ `apply.md` ระบุว่า
"ควรใส่เสมอ" และ repo นี้กำลังจะรับ contributor จากภายนอก การมี header ตั้งแต่ไฟล์แรก
ทำให้ไฟล์ใหม่ที่คนอื่นเขียนเข้ามาลอกรูปแบบตามได้เอง

## เรื่องที่ตรวจแล้วไม่ต้องถาม

**dependency compatibility** — `go.mod` มี direct dependency 3 ตัว ตรวจจาก GitHub API แล้ว:
`go-chi/chi` = MIT, `redis/go-redis` = BSD-2-Clause, `uber-go/zap` = MIT
permissive ทั้งหมด → ไหลเข้า AGPL-3.0 ได้อิสระตามกฎทิศทางเดียว ไม่มีข้อขัดแย้งให้รายงาน
