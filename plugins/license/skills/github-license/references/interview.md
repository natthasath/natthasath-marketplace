# Decision Tree — คำถามที่ใช้ถามผู้ใช้

เกณฑ์การตัดสินใจของ skill นี้ ออกแบบมาสำหรับ**คนที่ไม่รู้เรื่องลิขสิทธิ์หรือสิทธิบัตรเลย**

## หลักการถาม

**ห้ามถามด้วยศัพท์ ถามด้วยสถานการณ์** — คนที่ไม่รู้เรื่อง license ตอบคำถามว่า "คุณต้องการ copyleft ไหม" ไม่ได้
แต่ตอบคำถามว่า "ถ้ามีบริษัทเอาโค้ดคุณไปขาย คุณรู้สึกยังไง" ได้ทันที เพราะเป็นเรื่องความรู้สึกและผลลัพธ์ที่เขาจินตนาการออก
คำว่า copyleft / permissive / patent grant / derivative work ให้เก็บไว้อธิบายตอนสรุปผลลัพธ์ ไม่ใช่ตอนถาม

**ถามทีละข้อด้วย AskUserQuestion** — คนที่ไม่รู้เรื่องจะจมทันทีถ้าเจอ 5 คำถามพร้อมกัน
การถามทีละข้อยังทำให้ตัดกิ่งที่ไม่เกี่ยวออกได้ — ถ้าตอบข้อ 2 ว่า "ใครเอาไปทำอะไรก็ได้" ก็ไม่ต้องถามเรื่อง SaaS เลย

**อย่าถามสิ่งที่อ่านเอาเองได้** — ภาษาที่ใช้, dependency, ชื่อเจ้าของ, ปี, ประเภทโปรเจกต์ ดูจาก repo ได้หมด
ถามเฉพาะสิ่งที่อยู่ในหัวผู้ใช้เท่านั้น: **เขาอยากให้คนอื่นทำอะไรกับงานเขาได้บ้าง**

**เป้าหมายคือ 3-5 คำถาม** เส้นทางส่วนใหญ่จบใน 3 คำถาม เกิน 5 เมื่อไหร่แปลว่าถามละเอียดเกินจำเป็น

---

## Step 0 — อ่าน repo ก่อนถามคำถามแรก

| สิ่งที่ต้องหา | หาจาก | เอาไปใช้ทำอะไร |
|---|---|---|
| มี `LICENSE` อยู่แล้วไหม | `LICENSE*`, `COPYING*` ที่ root | ถ้ามี → ดูหัวข้อ "กรณีมี license อยู่แล้ว" |
| ประเภทงาน | ไฟล์ในโปรเจกต์ — มีแต่ `.md`/`.csv`/`.png` หรือมีโค้ดจริง | ตอบ Q1 เองได้เลย เหลือแค่ยืนยัน |
| ภาษา / ecosystem | `package.json`, `pyproject.toml`, `Cargo.toml`, `go.mod`, `pom.xml`, `composer.json` | เลือก metadata field ที่ต้องอัปเดต + เดา license ที่วงการนั้นนิยม |
| dependency licenses | ไฟล์ manifest ข้างต้น | ตรวจความเข้ากันได้ตาม `compatibility.md` |
| ชื่อเจ้าของ | `git config user.name`, field `author` ใน manifest, remote URL | เอาไปเป็นค่าตั้งต้นให้ผู้ใช้ยืนยัน ไม่ต้องถามลอย ๆ |
| เป็น library หรือ application | มี entry point ที่รันเองได้ vs. ถูก import อย่างเดียว | ใช้ตัดสินระหว่าง GPL กับ LGPL/MPL |

## Q1 — งานนี้เป็นอะไร

> "โปรเจกต์นี้เป็นงานแบบไหนครับ"

| ตัวเลือกที่แสดง | ไปต่อที่ |
|---|---|
| โปรแกรม / โค้ด / library | **Q2** |
| เอกสาร บทความ คอร์สเรียน สไลด์ | **Q6 (สาย CC)** |
| ชุดข้อมูล (dataset) | **Q6 (สาย CC)** |
| รูป เสียง วิดีโอ งานออกแบบ | **Q6 (สาย CC)** |

**ถ้าอ่าน repo แล้วชัดเจนอยู่แล้ว** ให้ข้ามคำถามนี้ไปเลย แล้วบอกผู้ใช้ว่า "เห็นว่าเป็นโปรเจกต์ Python ผมจะถามในมุมของซอฟต์แวร์นะครับ"
การถามสิ่งที่เห็นอยู่แล้วทำให้ผู้ใช้รู้สึกว่าเสียเวลา

**ถ้าเป็นโค้ด + เอกสารปนกันจริงจัง** (เช่น repo ที่มีทั้ง source และหนังสือ) ให้เดินสาย Q2 ก่อน แล้วค่อยเสนอเพิ่มตอนสรุปว่าอาจใส่ CC ให้โฟลเดอร์เอกสารแยก

## Q2 — คำถามหัวใจ

คำถามนี้ตัดสิน 80% ของผลลัพธ์ ถ้าถามได้ดีที่เหลือแทบไม่ต้องคิด

> "สมมติมีบริษัทหนึ่งเอาโปรเจกต์นี้ไปใส่ในสินค้าที่เขาขายได้เงินเป็นล้าน
> เขาไม่เปิดโค้ดอะไรเลย ไม่แบ่งเงินคุณ แค่เขียนชื่อคุณไว้เล็ก ๆ ในหน้าเครดิต
> — คุณรู้สึกยังไงครับ"

| ตัวเลือกที่แสดง | ความหมายจริง | ไปต่อที่ |
|---|---|---|
| "ดีใจสิ ยิ่งมีคนใช้เยอะยิ่งดี" | permissive | **Q3** |
| "ได้ แต่ถ้าเขาแก้โค้ดของผม เขาต้องเปิดส่วนที่แก้ให้คนอื่นเห็นด้วย" | copyleft | **Q4** |
| "ไม่โอเค ถ้าจะเอาไปหาเงิน ต้องมาคุยกับผมก่อน" | source-available / noncommercial | **Q5** |

**ถ้าผู้ใช้ลังเลหรือตอบว่าไม่รู้:** อย่าถามซ้ำด้วยคำถามเดิม ให้ถามให้แคบลงแทน — "ถ้าไม่คิดเรื่องเงิน คุณอยากให้โปรเจกต์นี้ถูกใช้กว้างที่สุดเท่าที่จะเป็นไปได้ หรืออยากคุมว่าใครใช้ได้บ้าง"
ถ้ายังไม่ชัด ให้เลือก **MIT** แล้วบอกตรง ๆ ว่า "ผมเลือก MIT ให้นะครับ เป็นตัวที่คนใช้เยอะที่สุดและปลอดภัยที่สุดเมื่อยังไม่มีเงื่อนไขพิเศษ ถ้าวันหลังเปลี่ยนใจ เปลี่ยนได้ตราบใดที่ยังไม่มีคนอื่นมาร่วมเขียนโค้ด"

## Q3 — สาย Permissive

> "ในโปรเจกต์นี้มีวิธีการหรืออัลกอริทึมที่คุณคิดขึ้นเองแบบใหม่ ๆ ไหม
> หรือมันเป็นงานที่ทำในนามบริษัท/หน่วยงาน"

| ตัวเลือกที่แสดง | ผลลัพธ์ |
|---|---|
| "มี / เป็นงานบริษัท / อยากให้องค์กรใหญ่กล้าเอาไปใช้" | **`Apache-2.0`** |
| "ไม่มีอะไรพิเศษ ขอแบบสั้นและง่ายที่สุด" | **`MIT`** |
| "ไม่อยากให้ใครเอาชื่อผม/ชื่อหน่วยงานไปอ้างว่ารับรองสินค้าเขา" | **`BSD-3-Clause`** |
| "ไม่ต้องให้เครดิตผมก็ได้ ยกให้เป็นของสาธารณะไปเลย" | **`Unlicense`** + เตือนข้อจำกัดตาม `catalog.md` |

**ตัวสำรองที่ไม่ต้องถาม แต่เสนอได้ถ้า ecosystem ชี้ชัด** — เสนอเป็นทางเลือกตอนสรุป ไม่ใช่เพิ่มคำถาม:
- npm package → `ISC` (สั้นกว่า MIT ผลเท่ากัน npm เองใช้ตัวนี้)
- C++ / Boost → `BSL-1.0`
- เกม / graphics / library ระดับล่าง → `Zlib`
- โปรเจกต์ที่ต้องเข้ากับ BSD-family เดิม → `BSD-2-Clause`

## Q4 — สาย Copyleft

ถามสองข้อ ข้อแรกตัด AGPL ออกหรือเข้า ข้อที่สองเลือกความเข้ม

### Q4a — เรื่องคลาวด์

> "ถ้ามีคนไม่ได้แจกโปรแกรม แต่เอาโค้ดคุณไปรันเป็นเว็บหรือ API บนคลาวด์ แล้วเก็บเงินคนใช้
> — เขาควรต้องเปิดโค้ดด้วยไหมครับ"

| ตัวเลือกที่แสดง | ผลลัพธ์ |
|---|---|
| "ต้องเปิด ไม่งั้นก็เลี่ยงกฎได้ง่ายเกินไป" | **`AGPL-3.0`** — จบ ไม่ต้องถาม Q4b |
| "ไม่ต้องก็ได้ ขอแค่ตอนแจกโปรแกรมออกไปแล้วเปิดก็พอ" | ไป **Q4b** |
| "โปรเจกต์นี้ไม่ได้เป็นเว็บหรือบริการออนไลน์" | ไป **Q4b** |

ถ้าเลือก AGPL ต้องเตือนให้ชัดว่า Google และองค์กรใหญ่หลายแห่งมีนโยบายห้ามใช้ซอฟต์แวร์ AGPL — นี่คือราคาที่ต้องจ่าย และบางครั้งก็คือจุดประสงค์

### Q4b — ขอบเขตความเข้ม

> "โปรแกรมปิดโค้ดของบริษัทอื่น ควรเรียกใช้โปรเจกต์นี้ได้ไหม โดยที่เขาไม่ต้องเปิดโค้ดตัวเอง"

| ตัวเลือกที่แสดง | ผลลัพธ์ |
|---|---|
| "ไม่ได้ ใครเอาไปใช้ต้องเปิดทั้งโปรแกรม" | **`GPL-3.0`** |
| "ได้ ตราบใดที่เขาไม่ได้แก้ของผม — ถ้าแก้ ต้องเปิดเฉพาะไฟล์ที่แก้" | **`MPL-2.0`** |

**เมื่อไหร่ถึงเสนอ `LGPL-3.0` แทน MPL-2.0:** เฉพาะเมื่อโปรเจกต์เป็น library ที่ถูก link เข้าไปในโปรแกรมอื่น **และ** ผู้ใช้ต้องการให้ผู้ใช้ปลายทางเปลี่ยน library เป็นเวอร์ชันของตัวเองได้
LGPL ทำตามยากกว่า MPL มากใน static linking และแอปมือถือ — ถ้าไม่มีเหตุผลชัดเจน MPL-2.0 คือคำตอบที่ดีกว่าสำหรับคนที่เพิ่งเริ่ม

**เมื่อไหร่ถึงเสนอ `EPL-2.0`:** โปรเจกต์อยู่ในระบบนิเวศ Eclipse / Jakarta EE / Java enterprise
**เมื่อไหร่ถึงเสนอ `GPL-2.0` / `LGPL-2.1`:** ต้องเข้ากับ Linux kernel หรือโปรเจกต์เดิมที่ตรึงอยู่ที่รุ่น 2 เท่านั้น — ปกติเลือกรุ่น 3 เสมอ

## Q5 — สาย Source-available

**ก่อนถาม ต้องบอกความจริงข้อนี้ก่อนเสมอ:** กลุ่มนี้ไม่นับเป็น open source ตามนิยามสากล
คนจะ contribute น้อยลง, distro อย่าง Debian/Fedora จะไม่รับเข้า repository, และบางบริษัทมีนโยบายห้ามใช้
ถ้าผู้ใช้ไม่ได้กำลังทำ product เชิงพาณิชย์จริง ๆ ให้ชวนกลับไปดู `AGPL-3.0` ซึ่งกันคู่แข่งได้มากพอสมควรโดยยังเป็น open source

> "แล้วอีก 4 ปีข้างหน้า ถ้าโค้ดชุดนี้เปิดเป็น open source เต็มตัว คุณโอเคไหมครับ"

| ตัวเลือกที่แสดง | ผลลัพธ์ |
|---|---|
| "โอเค อยากให้สุดท้ายมันเปิด แค่ขอกันช่วงที่ยังทำเงินอยู่" | **`BUSL-1.1`** — ต้องถามค่าพารามิเตอร์ต่อ |
| "ไม่ ขอปิดตลอด แต่ห้ามแค่คนเอาไปทำบริการมาแข่งกับผม" | **`Elastic-2.0`** |
| "ห้ามเอาไปหาเงินเลย ยกเว้นมาซื้อ license จากผม" | **`PolyForm-Noncommercial-1.0.0`** |
| "ใครเอาไปเปิดเป็นบริการ ต้องเปิดทุกอย่างที่ใช้รันบริการนั้น" | **`SSPL-1.0`** + เตือนว่าเข้มที่สุดและถูกต่อต้านมากที่สุด |

### ค่าที่ต้องถามเพิ่มเมื่อเลือก `BUSL-1.1`

BUSL ที่ไม่กรอกค่าเหล่านี้ = license ที่ไม่สมบูรณ์ ต้องถามให้ครบ พร้อมเสนอค่าตั้งต้น:

| ค่า | คำถาม | ค่าตั้งต้นที่แนะนำ |
|---|---|---|
| Licensor | ใครเป็นเจ้าของ (ชื่อคนหรือชื่อบริษัท) | จาก git config |
| Licensed Work | ชื่อโปรเจกต์ | ชื่อ repo |
| Change Date | วันที่จะกลายเป็น open source | วันนี้ + 4 ปี |
| Change License | จะเปลี่ยนเป็น license อะไร | `Apache-2.0` (ต้องเข้ากับ GPL-2.0 ขึ้นไปตามข้อกำหนดของ BUSL) |
| Additional Use Grant | ยอมให้ใช้ในงานจริงได้แค่ไหนโดยไม่ต้องซื้อ | `None` หรือแบบที่ Sentry/HashiCorp ใช้: อนุญาตทุกการใช้งานที่ไม่ใช่การเอาไปให้บริการแข่งกับผลิตภัณฑ์ของผู้ให้สิทธิ์ |
| Contact Info | ติดต่อซื้อ license ที่ไหน | อีเมลจาก git config |

## Q6 — สาย Creative Commons (งานที่ไม่ใช่โค้ด)

> "อยากให้คนอื่นเอางานนี้ไปใช้ได้แค่ไหนครับ"

| ตัวเลือกที่แสดง | ผลลัพธ์ |
|---|---|
| "ใช้ได้เต็มที่ ขายได้ด้วย แค่ให้เครดิตผม" | **`CC-BY-4.0`** |
| "ใช้ได้ แต่ถ้าเอาไปต่อยอด งานใหม่ต้องเปิดให้คนอื่นใช้ต่อเหมือนกัน" | **`CC-BY-SA-4.0`** |
| "ห้ามเอาไปหาเงิน" | **`CC-BY-NC-4.0`** + คำเตือนเรื่องนิยาม "เชิงพาณิชย์" ที่ไม่ชัดเจน |
| "ยกให้เป็นสมบัติสาธารณะ ไม่ต้องให้เครดิตก็ได้" | **`CC0-1.0`** |

**สำหรับ dataset โดยเฉพาะ:** ส่วนใหญ่จบที่ `CC0-1.0` (เปิดสุด ใช้ในงานวิจัยง่ายที่สุด) หรือ `CC-BY-4.0` (ขอเครดิต) — ถ้าผู้ใช้ไม่มีความเห็นชัดเจน แนะนำ `CC-BY-4.0`

## คำถามที่ถามเฉพาะเมื่อเจอสัญญาณ

ห้ามถามชุดนี้ทุกครั้ง — ถามเฉพาะเมื่อ Step 0 หรือคำตอบก่อนหน้าจุดชนวนขึ้นมา
คนที่ไม่รู้เรื่องลิขสิทธิ์มักไม่รู้ว่าประเด็นเหล่านี้มีอยู่ การถามตอนที่เกี่ยวข้องจริงคือคุณค่าหลักของ skill นี้

### มี LICENSE อยู่แล้ว

> "เห็นว่ามีไฟล์ LICENSE เป็น {ตัวเดิม} อยู่แล้ว ต้องการเปลี่ยนเป็นตัวใหม่ หรือแค่มาดูว่าตัวเดิมเหมาะไหมครับ"

ถ้าจะเปลี่ยนจริง ต้องบอกให้ชัดว่า: **โค้ดที่เผยแพร่ไปแล้วภายใต้ license เดิมจะยังใช้เงื่อนไขเดิมได้ตลอดไป เพิกถอนย้อนหลังไม่ได้**
และถ้ามีคนอื่นเคย commit เข้ามา ต้องได้รับความยินยอมจากทุกคนก่อน (ยกเว้นมี CLA)
ตรวจจำนวนผู้ร่วมพัฒนาด้วย `git shortlog -sne` แล้วรายงานตัวเลขจริงให้ผู้ใช้ตัดสินใจ

### งานที่ทำในเวลางาน / ด้วยทรัพยากรของนายจ้าง / ทุนวิจัย

จุดชนวน: ผู้ใช้พูดถึงบริษัท หน่วยงาน มหาวิทยาลัย หรือ email ใน git config เป็นโดเมนองค์กร

> "โค้ดนี้เขียนตอนทำงานประจำ หรือใช้อุปกรณ์/เวลาของที่ทำงานไหมครับ
