## กลุ่ม 1 — Permissive

> "เอาไปทำอะไรก็ได้ แค่ให้เครดิตฉัน และถ้าพังอย่ามาโทษฉัน"

ทางเลือกที่คนใช้กันมากที่สุดในโลก open source ประมาณ 60-70% ของ repo บน GitHub อยู่ในกลุ่มนี้
เหมาะกับคนที่อยากให้ของตัวเองถูกใช้ให้กว้างที่สุด และไม่ซีเรียสว่าใครจะเอาไปทำเงิน

### `MIT` — ค่าเริ่มต้นที่ปลอดภัยที่สุด

สั้น อ่านจบใน 1 นาที ทุกฝ่ายคุ้นเคย ทนายบริษัทไม่ต้องคิดเยอะ
**ใช้เมื่อ:** ไม่รู้จะเลือกอะไร และไม่มีเงื่อนไขพิเศษ
**ตัวอย่าง:** React, Vue, Rails, jQuery, .NET, Bootstrap
**ข้อควรรู้:** ไม่พูดถึงสิทธิบัตรเลย ถ้าโปรเจกต์คุณมีอัลกอริทึมที่อาจจดสิทธิบัตรได้ ให้ดู Apache-2.0 แทน

### `ISC` — MIT ฉบับกระชับกว่า

เนื้อหาเทียบเท่า MIT แต่ตัดถ้อยคำซ้ำซ้อนออก มีผลทางกฎหมายเหมือนกัน
**ใช้เมื่อ:** ชอบ MIT แต่อยากได้ไฟล์สั้นกว่า / ทำ npm package (npm เองใช้ ISC)
**ตัวอย่าง:** npm, OpenBSD

### `BSD-2-Clause` — เทียบเท่า MIT

เรียกอีกชื่อว่า "Simplified BSD" ใช้แทน MIT ได้เลย ต่างกันแค่สำนวน
**ใช้เมื่อ:** อยู่ในวงการที่ใช้ BSD กันอยู่แล้ว (ระบบปฏิบัติการ, งานวิชาการ, C/C++)

### `BSD-3-Clause` — BSD-2 + ห้ามเอาชื่อฉันไปโฆษณา

เพิ่มข้อเดียว: ห้ามใช้ชื่อผู้เขียนหรือชื่อองค์กรไปรับรอง/โปรโมตสินค้าที่ต่อยอด โดยไม่ขออนุญาต
**ใช้เมื่อ:** กลัวคนเอาชื่อคุณหรือชื่อหน่วยงานไปอ้างว่า "รับรองสินค้านี้"
**ตัวอย่าง:** Go, Django, NumPy, Pandas

### `Apache-2.0` — permissive สำหรับงานที่จริงจัง

เหมือน MIT ในแง่เสรีภาพ แต่เพิ่ม 3 อย่างที่บริษัทใหญ่ต้องการ:
1. **ให้สิทธิ์การใช้สิทธิบัตรชัดเจน** — ผู้ร่วมพัฒนาให้สิทธิ์สิทธิบัตรของตัวเองมาด้วย
2. **ถ้าใครฟ้องสิทธิบัตรคุณ สิทธิ์ของเขาถูกยกเลิกทันที** (patent retaliation)
3. **ต้องระบุว่าแก้อะไรไป** และต้องส่งต่อไฟล์ `NOTICE` ถ้ามี

**ใช้เมื่อ:** โปรเจกต์เป็นงานบริษัท / มีผู้ร่วมพัฒนาหลายองค์กร / เกี่ยวข้องกับอัลกอริทึมหรือ AI model / อยากให้บริษัทใหญ่กล้าใช้
**ตัวอย่าง:** Kubernetes, Android, TensorFlow, Swift, Kafka
**ข้อควรรู้:** เข้ากับ GPL-2.0 ไม่ได้ (ดู `compatibility.md`) แต่เข้ากับ GPL-3.0 ได้

### `BSL-1.0` — Boost Software License

permissive และเป็นตัวเดียวในกลุ่มที่**ไม่บังคับให้แนบ license ตอนแจกไฟล์ binary** สะดวกกับซอฟต์แวร์ฝังตัว
**ใช้เมื่อ:** ทำ C++ library โดยเฉพาะสาย Boost
**ระวังสับสน:** `BSL-1.0` (Boost, permissive) ≠ `BUSL-1.1` (Business Source License, source-available) คนละตัวคนละโลก

### `Zlib` — permissive สำหรับ library เล็ก ๆ

สั้นมาก มีข้อเดียวที่เพิ่มมา: ถ้าแก้แล้วแจกต่อ ต้องระบุให้ชัดว่าเวอร์ชันนี้ถูกแก้ ห้ามอ้างว่าเป็นต้นฉบับ
**ใช้เมื่อ:** ทำ library ระดับล่าง, เกม, กราฟิก
**ตัวอย่าง:** zlib, SDL

## กลุ่ม 2 — Public Domain

> "ฉันสละสิทธิ์ทั้งหมด เอาไปเลย ไม่ต้องให้เครดิตด้วยซ้ำ"

ต่างจาก permissive ตรงที่ไม่บังคับแม้แต่การให้เครดิต

### `Unlicense` — สละสิทธิ์แบบตรงไปตรงมา

**ใช้เมื่อ:** โค้ดตัวอย่าง, snippet, งานที่อยากให้ก๊อปไปใช้ได้โดยไม่ต้องคิดอะไรเลย
**ข้อควรรู้:** บางประเทศ (รวมถึงหลายประเทศในยุโรป) ไม่ยอมรับการสละลิขสิทธิ์โดยสมบูรณ์ ทำให้สถานะทางกฎหมายไม่แน่นอน ถ้าเป็นงานที่จริงจังใช้ MIT ปลอดภัยกว่า

### `CC0-1.0` — สละสิทธิ์ฉบับที่ทนายยอมรับมากกว่า

ออกแบบมาให้รองรับประเทศที่สละลิขสิทธิ์ไม่ได้ โดยมี fallback เป็นการให้สิทธิ์แบบกว้างที่สุดแทน
**ใช้เมื่อ:** dataset, ผลงานวิจัย, งานที่อยากให้เป็นสมบัติสาธารณะจริง ๆ
**ข้อควรรู้สำคัญ:** CC0 **ระบุชัดว่าไม่ให้สิทธิ์สิทธิบัตร** — ห้ามใช้กับซอฟต์แวร์ที่อาจมีประเด็นสิทธิบัตร (Fedora และหลายองค์กรห้ามใช้ CC0 กับโค้ดด้วยเหตุผลนี้) ใช้กับ**ข้อมูล**เหมาะกว่าใช้กับ**โค้ด**

## กลุ่ม 3 — Weak Copyleft

> "แก้ของฉันตรงไหน เปิดตรงนั้น ส่วนโค้ดของคุณเองปิดไว้ได้"

ทางสายกลาง — ป้องกันไม่ให้ใครเอาโค้ดคุณไปปิดแล้วหายไป แต่ก็ไม่ไปบังคับให้เขาต้องเปิดทั้งโปรแกรม
เหมาะกับ library ที่อยากให้ทั้งโลกใช้ รวมถึงซอฟต์แวร์ปิดโค้ด

### `MPL-2.0` — ขอบเขตอยู่ที่ "ไฟล์"

ใครแก้ไฟล์ไหนของคุณ ต้องเปิดไฟล์นั้น ไฟล์ใหม่ที่เขาเขียนเองปิดได้ทั้งหมด
เข้าใจง่ายที่สุดในกลุ่มนี้เพราะขอบเขตชัด: นับเป็นรายไฟล์
**ใช้เมื่อ:** อยากได้ copyleft ที่ไม่ทำให้บริษัทกลัว / ทำ library หรือ tool ที่ต้องถูกฝังในระบบใหญ่
**ตัวอย่าง:** Firefox, Terraform (ก่อนเวอร์ชัน 1.5), Consul (เดิม)

### `LGPL-3.0` — ขอบเขตอยู่ที่ "ตัวไลบรารี"

โปรแกรมปิดโค้ดเรียกใช้ library คุณได้ แต่ถ้าเขาแก้ตัว library เอง ต้องเปิดส่วนนั้น
และเขาต้องทำให้ผู้ใช้ปลายทาง**เปลี่ยน library เป็นเวอร์ชันอื่นได้เอง** (relink) ซึ่งเป็นเงื่อนไขที่ทำตามยากใน static linking และในแอปมือถือ
**ใช้เมื่อ:** ทำ library ที่ต้องการ copyleft แต่ยอมให้ฝังในซอฟต์แวร์ปิด
**ตัวอย่าง:** Qt, GTK, glibc (LGPL-2.1)
**ข้อควรรู้:** ไฟล์ `LGPL-3.0.txt` เป็นแค่ส่วนเสริมของ GPL-3.0 — ต้องแนบข้อความ GPL-3.0 ไปด้วยเสมอ ดูขั้นตอนใน `apply.md`

### `LGPL-2.1` — LGPL รุ่นเก่า

ยังพบมากในโปรเจกต์เก่าและวงการ C/embedded ไม่มีข้อกำหนดเรื่องสิทธิบัตรแบบ 3.0
**ใช้เมื่อ:** ต้องเข้ากับระบบนิเวศเดิมที่ใช้ LGPL-2.1 หรือต้องเข้ากับ GPL-2.0

### `EPL-2.0` — copyleft ของโลก Java

คล้าย MPL (ขอบเขตรายไฟล์) แต่มีเงื่อนไขเรื่องการชดใช้ค่าเสียหายเชิงพาณิชย์เพิ่ม
**ใช้เมื่อ:** โปรเจกต์อยู่ในระบบนิเวศ Eclipse / Jakarta EE / Java enterprise
**ตัวอย่าง:** Eclipse IDE, Jakarta EE, Clojure (EPL-1.0)

## กลุ่ม 4 — Strong Copyleft

> "ใครเอาของฉันไปใส่ในโปรแกรมอะไร โปรแกรมนั้นทั้งก้อนต้องเปิดโค้ดด้วย"

เรียกกันว่า "ไวรัล" (viral) เพราะเงื่อนไขติดไปกับทุกอย่างที่มันไปแตะ
เป็นเครื่องมือทางอุดมการณ์ — ใช้เมื่ออยากบังคับให้ทุกคนที่ต่อยอดต้องแบ่งปันกลับ

### `GPL-3.0` — มาตรฐานของ strong copyleft ยุคนี้

ใครแจกโปรแกรมที่มีโค้ดคุณอยู่ ต้องแจก source code ทั้งหมดภายใต้ GPL-3.0 เหมือนกัน
เพิ่มจาก 2.0: ให้สิทธิ์สิทธิบัตรชัดเจน และห้าม "tivoization" (ขายฮาร์ดแวร์ที่ล็อกไม่ให้ผู้ใช้ลงเวอร์ชันที่แก้เอง)
**ใช้เมื่อ:** ทำแอปพลิเคชันสำหรับผู้ใช้ปลายทาง และไม่อยากให้ใครเอาไปทำเป็นสินค้าปิดโค้ด
**ตัวอย่าง:** GIMP, Inkscape, Bash, GNU tools

### `GPL-2.0` — GPL รุ่นเก่า

ไม่มีเงื่อนไขสิทธิบัตรและไม่มีข้อห้าม tivoization
**ใช้เมื่อ:** ต้องเข้ากับ Linux kernel หรือระบบนิเวศเดิมที่ตรึงอยู่ที่ 2.0
**ตัวอย่าง:** Linux kernel, Git
**ข้อควรรู้:** เข้ากับ Apache-2.0 ไม่ได้ ถ้าโปรเจกต์คุณมี dependency Apache-2.0 อย่าเลือกตัวนี้

### `AGPL-3.0` — GPL ที่อุดช่องโหว่ SaaS

GPL ปกติมีช่องว่าง: ถ้าบริษัทเอาโค้ดคุณไปรันเป็นเว็บ/API ให้คนใช้ **โดยไม่แจกไฟล์โปรแกรม** เขาไม่ต้องเปิดโค้ดเลย
AGPL อุดช่องนี้ — ให้ถือว่า "การให้บริการผ่านเครือข่าย" เท่ากับการแจกจ่าย
**ใช้เมื่อ:** ทำ server, backend, self-hosted app แล้วกลัว cloud provider เอาไปขายเป็นบริการทับ
**ตัวอย่าง:** Mastodon, Nextcloud, Grafana, MinIO
**ข้อควรรู้:** Google และบริษัทใหญ่หลายแห่งมีนโยบายห้ามพนักงานใช้ซอฟต์แวร์ AGPL — เลือกตัวนี้แล้วต้องยอมรับว่าองค์กรใหญ่จะหลบ ซึ่งบางครั้งนั่นคือจุดประสงค์

## กลุ่ม 5 — Creative Commons

> สำหรับงานที่ **ไม่ใช่โค้ด** — เอกสาร บทความ รูป เสียง วิดีโอ สไลด์ dataset

**ห้ามใช้ CC กับซอร์สโค้ด** — Creative Commons เองก็แนะนำแบบนี้ เพราะ CC ไม่ได้พูดถึงเรื่อง source code, การ link, หรือสิทธิบัตร ซึ่งเป็นหัวใจของ license ซอฟต์แวร์

| ตัวเลือก | ให้อะไร | ห้ามอะไร |
|---|---|---|
| `CC-BY-4.0` | เอาไปใช้ ดัดแปลง ขายได้ | ต้องให้เครดิต |
| `CC-BY-SA-4.0` | เหมือน BY | + งานต่อยอดต้องใช้ license เดียวกัน (แบบ Wikipedia) |
| `CC-BY-NC-4.0` | เอาไปใช้ ดัดแปลงได้ | ⛔ ห้ามใช้เชิงพาณิชย์ |

**เตือนเรื่อง `CC-BY-NC-4.0`:** คำว่า "เชิงพาณิชย์" ไม่มีนิยามที่ชัดเจนในสัญญา ทำให้เกิดพื้นที่สีเทาเยอะมาก
(บล็อกที่มีโฆษณานับไหม? องค์กรไม่แสวงหากำไรใช้ในงานอบรมที่เก็บค่าลงทะเบียนนับไหม?)
ผลคือคนจำนวนมากเลือกที่จะไม่ใช้เลยเพราะไม่กล้าเสี่ยง — และมันไม่ถือเป็น open source / free culture
ถ้าเป้าหมายจริง ๆ คือ "อยากได้เงินถ้ามีคนเอาไปทำธุรกิจ" การใช้ `BUSL-1.1` หรือขาย commercial license แยกตรงกว่า

**สำหรับ dataset:** `CC0-1.0` (สาธารณะ) หรือ `CC-BY-4.0` (ขอเครดิต) คือสองตัวที่ใช้กันมากที่สุด

## กลุ่ม 6 — Source-available

> "เห็นโค้ดได้ แก้ได้ แต่ห้ามเอาไปแข่งกับฉัน"

**กลุ่มนี้ไม่ใช่ open source** ตามนิยามของ OSI และ Free Software Foundation — ต้องบอกผู้ใช้ให้ชัด
ห้ามติด badge "open source" หรือ "OSI approved" และ GitHub จะไม่แสดง license label ให้บาง repo ในกลุ่มนี้

เกิดขึ้นเพราะปัญหาจริง: บริษัทสร้างซอฟต์แวร์ open source แล้ว cloud provider เอาไปขายเป็น managed service ทำเงินมหาศาลโดยไม่ต้องแบ่งอะไรกลับมา

### `BUSL-1.1` — Business Source License (open source แบบหน่วงเวลา)

ปิดตอนแรก แล้ว**เปลี่ยนเป็น open source อัตโนมัติ**เมื่อถึงวันที่กำหนด (Change Date ปกติตั้งไว้ 4 ปี)
เป็นตัวเลือกที่ "ใจกว้าง" ที่สุดในกลุ่มนี้ เพราะให้สัญญาชัดเจนกับชุมชนว่าสุดท้ายจะเปิด
**ใช้เมื่อ:** ทำ product เชิงพาณิชย์ แต่อยากให้โค้ดเปิดในระยะยาว
**ตัวอย่าง:** Terraform (1.5+), Sentry, CockroachDB, MariaDB MaxScale
**ต้องกรอก 5 ค่า** ก่อนใช้งานได้ ไม่งั้น license ไม่สมบูรณ์ — ดู `apply.md`

### `Elastic-2.0` — ห้ามเอาไปทำ managed service

อนุญาตแทบทุกอย่าง ยกเว้น 3 ข้อ: (1) เอาไปให้บริการเป็น managed/hosted service กับคนอื่น (2) ปลดล็อกฟีเจอร์ที่ล็อกด้วย license key (3) ลบ/แก้ประกาศลิขสิทธิ์
**ใช้เมื่อ:** ทำ infrastructure product ที่กลัว cloud provider โดยเฉพาะ และไม่อยากให้ผู้ใช้ทั่วไปมีภาระอะไรเลย
**ตัวอย่าง:** Elasticsearch, Kibana

### `SSPL-1.0` — ถ้าเปิดให้บริการ ต้องเปิดทั้ง stack

ถ้าคุณเอาซอฟต์แวร์นี้ไปให้บริการคนอื่น คุณต้องเปิด source code ของ**ทุกอย่างที่ใช้ให้บริการนั้น** — รวม management tool, monitoring, provisioning, ทุกชิ้น
เงื่อนไขนี้กว้างจนแทบไม่มีใครทำตามได้จริง ซึ่งคือความตั้งใจ
**ใช้เมื่อ:** ต้องการปิดกั้น cloud provider แบบเด็ดขาด และรับได้ว่าชุมชนส่วนใหญ่จะต่อต้าน
**ตัวอย่าง:** MongoDB
**ข้อควรรู้:** Debian, Fedora, Red Hat และ distro หลัก ๆ ถอดซอฟต์แวร์ SSPL ออกจาก repository ทั้งหมด

### `PolyForm-Noncommercial-1.0.0` — ห้ามค้าขาย ภาษาอ่านง่าย

ใช้ฟรีสำหรับงานส่วนตัว งานวิจัย การศึกษา องค์กรไม่แสวงหากำไร — ห้ามใช้เชิงพาณิชย์
เขียนด้วยภาษาสมัยใหม่ที่อ่านเข้าใจได้จริง และให้นิยาม "noncommercial" ชัดกว่า CC-BY-NC
**ใช้เมื่อ:** อยากให้คนเรียน/นักวิจัยใช้ฟรี แต่บริษัทต้องมาซื้อ license
**โมเดลที่ใช้คู่กัน:** ปล่อยตัวนี้เป็น default แล้วขาย commercial license แยกให้บริษัท (dual licensing)
