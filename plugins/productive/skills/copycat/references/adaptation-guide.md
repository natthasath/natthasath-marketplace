# วิธีประเมินและดัดแปลง skill ต้นทาง

อ่านไฟล์นี้หลังจากดึงเนื้อหา skill ต้นทางมาแล้ว ก่อนเริ่มเขียนไฟล์ใหม่ — เป้าหมายของขั้นนี้คือ
แปลง skill ที่เขียนมาเพื่อคนอื่น ให้กลายเป็น skill ที่เข้ากับ environment และ convention ของผู้ใช้จริงๆ
ไม่ใช่แค่ copy-paste แล้วเปลี่ยนชื่อไฟล์

## 1. เช็ค dependency ภายนอกที่ skill ต้นทางพึ่งพา

หลายๆ skill ที่เจอตามอินเทอร์เน็ตเขียนโดยสมมติว่าเครื่องผู้ใช้มี CLI tool ติดตั้งไว้แล้ว (เช่น
เรียก `figlet`, `pandoc`, `imagemagick` ตรงๆ ผ่าน Bash) ก่อนย้ายมาเช็คว่า:

1. tool นั้นอยู่ในตาราง "Token-Efficient CLI Tools" ของผู้ใช้ (`CLAUDE.md` ส่วนตัว) หรือเครื่องนี้
   ติดตั้งไว้แล้วจริงไหม (ลองเช็คด้วย `which <tool>` หรือถามผู้ใช้ตรงๆ ถ้าไม่แน่ใจ)
2. ถ้า **ไม่มี** — อย่าเงียบๆ คง dependency นั้นไว้ในเวอร์ชันที่สร้างใหม่ ให้ถามผู้ใช้ก่อนเสมอว่า
   อยากได้แบบไหน:
   - **(a)** เรียก CLI tool จริงผ่าน Bash พร้อม install-check/install-prompt (แบบเดียวกับ
     `plugins/productive/skills/save-cost/SKILL.md`)
   - **(b)** bundle logic เทียบเท่าเป็น script ของตัวเอง (`scripts/`) ให้ทำงานได้โดยไม่ต้องติดตั้งอะไร
     เพิ่ม — ถ้า script ต้อง pip package ภายนอก (เช่น Pillow) ให้ใช้ PEP 723 inline metadata
     (`# /// script` block) แล้วสั่งรันผ่าน `uv run scripts/<name>.py` (เครื่องนี้มี `uv` ติดตั้งแล้ว
     จะจัดการ dependency ให้อัตโนมัติแบบ ephemeral ไม่ต้อง `pip install` เอง) — fallback เป็น
     `python3`/`python`/`py` ตามลำดับถ้า script ไม่มี dependency ภายนอกเลย
3. ถ้า tool ที่ skill ต้นทางระบุไว้ดู "เข้าใจผิด" ไม่ตรงกับสิ่งที่ skill นั้นควรทำจริงๆ (เช่น อ้างถึง
   tool ที่ทำหน้าที่ต่างไปจากที่ skill ต้องการ) ให้บอกผู้ใช้ตรงๆ แทนที่จะเงียบๆ ตัดทิ้งหรือใส่ตามเดิม

## 2. เช็ค license / การอ้างอิงต้นทาง

ถ้า skill ต้นทางมีไฟล์ LICENSE, ระบุชื่อผู้เขียนใน README/frontmatter, หรือมี copyright header —
**แจ้งผู้ใช้ในแชทเสมอ** ว่าต้นทางใช้ license อะไรและใครเป็นคนเขียน ก่อนดำเนินการต่อ (ผู้ใช้ของ
marketplace นี้เลือกไว้แล้วว่าไม่ต้องการให้ใส่ attribution comment ลงในไฟล์ที่สร้างใหม่ — แค่แจ้งให้รู้
ก็พอ ไม่ต้อง block การทำงานหรือถามยืนยันซ้ำ เว้นแต่ license นั้นเป็นแบบที่ restrictive ชัดเจน เช่น
ห้าม redistribute/modify — กรณีนั้นควรเตือนหนักขึ้นและถามก่อนไปต่อจริงๆ)

## 3. Generalize สิ่งที่เฉพาะเจาะจงกับคนอื่น

สแกนหา:
- Path เฉพาะเครื่องคนอื่น (เช่น `/Users/johndoe/...`, `C:\Users\someone\...`)
- ชื่อบริษัท/โปรเจกต์/API key ตัวอย่างที่ผูกกับบริบทของคนเขียนต้นฉบับ
- ภาษาที่ไม่ตรงกับที่ marketplace นี้ใช้ (ต้นทางส่วนใหญ่เป็นภาษาอังกฤษล้วน — ต้องแปล/เรียบเรียงใหม่
  เป็นภาษาไทยตาม pattern ใน `references/repo-pattern.md` ไม่ใช่แปลตรงตัวคำต่อคำ)

แล้วแทนที่ด้วยอะไรที่ generic หรือถามผู้ใช้ถ้าจำเป็นต้องรู้ค่าเฉพาะของเครื่องเขา (เช่น path ที่อยากให้
บันทึกไฟล์ผลลัพธ์ไว้)

## 4. เขียน description ใหม่ให้ manual-invoke-only ตาม pattern

Marketplace นี้ตั้งนโยบายว่าทุก skill ต้อง `disable-model-invocation: true` เสมอ (ยกเว้น plugin
`projects`) — ใส่ field นี้ในทุก skill ที่สร้างโดยไม่ต้องถามผู้ใช้ (เป็น default ของ repo นี้ไปแล้ว)

ถ้า description ของ skill ต้นทางเขียนแบบ pushy บอกให้ auto-trigger (เช่น "use this whenever...",
"always invoke when...") ให้ตัดส่วนนั้นออก แล้วเขียนใหม่ให้บอกแค่ว่า skill ทำอะไร ใช้ตอนไหน (สำหรับ
คนอ่าน ไม่ใช่สำหรับ trigger อัตโนมัติ) แล้วปิดท้ายด้วย "เรียกใช้ผ่าน `/skill-name` เท่านั้น —
ไม่ auto-trigger จากบทสนทนา" — ถ้า skill ต้นทางเดิมก็ manual-invoke-only อยู่แล้ว (มี field แบบ
`disable-model-invocation`/`disableModelInvocation` หรือคล้ายกัน) แปลว่า intent ตรงกับ pattern นี้
พอดี ไม่ต้องเปลี่ยนอะไรมาก แค่แปล/เรียบเรียงใหม่ตาม `references/repo-pattern.md` หัวข้อ 2

## 5. ตั้งชื่อ skill ใหม่

- ใช้ kebab-case เหมือนชื่อ skill อื่นๆ ในนี้ (เช่น `github-tag`, `session-name`, `save-cost`)
- ถ้าชื่อเดิมของ skill ต้นทางมี prefix/suffix ที่ไม่จำเป็น (เช่น "awesome-", "-tool", "-helper")
  ให้ตัดออก เสนอชื่อที่กระชับกว่า
- **เสนอชื่อที่คิดไว้ให้ผู้ใช้ยืนยันก่อนสร้างไฟล์จริงเสมอ** — อย่าตั้งชื่อเองแล้วสร้างไฟล์เลยโดยไม่ถาม

## 6. สรุปให้ผู้ใช้ก่อนถามเรื่อง plugin

ก่อนถามว่าจะใส่ plugin ไหน ให้สรุปสั้นๆ ให้ผู้ใช้เห็นภาพก่อนว่า:
1. skill ต้นทางทำอะไรได้บ้าง (สรุปจากที่อ่านมา ไม่ใช่ก็อปเนื้อหาต้นฉบับมาแปะ)
2. อะไรที่คิดว่าเหมาะกับผู้ใช้คนนี้โดยเฉพาะ (อิงจาก dependency ที่เจอในขั้น 1, ข้อจำกัด license
   ในขั้น 2, และสิ่งที่ generalize ไปในขั้น 3) — เช่น "skill นี้เดิมเรียก `pandoc` ตรงๆ แต่เครื่องนี้ไม่มี
   ติดตั้งไว้ เสนอให้ทำเป็น self-contained แทน" หรือ "เดิมเป็นภาษาอังกฤษเน้น B2B แต่ผู้ใช้ทำงานสาย
   IT ภาษาไทยเป็นหลัก เลยจะปรับ description เป็นภาษาไทยและตัวอย่างให้ตรงบริบทกว่านี้"

ค่อยถามว่าจะใส่ plugin ไหน (ดูตัวเลือกจาก `.claude-plugin/marketplace.json` ปัจจุบัน + ตัวเลือก
"สร้าง plugin ใหม่") แล้วค่อยถามยืนยันชื่อ skill ตามข้อ 5 — สองคำถามนี้ห้ามข้าม ต้องถามก่อนสร้างไฟล์
จริงเสมอ ไม่ว่าคำขอของผู้ใช้จะดูเร่งรีบแค่ไหน
