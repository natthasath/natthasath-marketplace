# Compatibility — ตรวจว่า license ที่เลือกขัดกับของที่ใช้อยู่ไหม

ผู้ใช้ที่ไม่รู้เรื่อง license แทบไม่มีทางรู้ประเด็นนี้เอง แต่มันเป็นจุดที่ผิดแล้วเดือดร้อนจริง
เพราะ **license ของสิ่งที่คุณหยิบมาใช้ เป็นตัวจำกัดว่า license ของคุณเลือกอะไรได้บ้าง**

เปรียบเทียบให้ผู้ใช้เข้าใจง่าย: ถ้ายืมของเขามาประกอบเป็นของเรา แล้วเขาบอกว่า "ยืมได้ แต่ของที่ประกอบเสร็จต้องแจกฟรีนะ"
เราจะเอาไปขายปิดโค้ดไม่ได้ ต่อให้โค้ดส่วนใหญ่เราเขียนเองก็ตาม

**ตรวจแค่ direct dependency ก็พอในทางปฏิบัติ** — transitive dependency ที่มีปัญหาจริงมักโผล่ผ่าน direct อยู่แล้ว
และการไล่ทั้ง tree ในโปรเจกต์ใหญ่กินเวลาเกินคุณค่าที่ได้

---

## กฎทิศทางเดียว

ความเข้ากันได้ของ license เป็น **ทิศทางเดียว** — A ใส่ใน B ได้ ไม่ได้แปลว่า B ใส่ใน A ได้

```
Public Domain  →  Permissive  →  Weak Copyleft  →  Strong Copyleft
(CC0/Unlicense)   (MIT/Apache)    (MPL/LGPL)        (GPL/AGPL)

ไหลไปทางขวาได้เสมอ · ไหลย้อนกลับซ้ายไม่ได้
```

แปลเป็นภาษาคน: **โค้ดที่เปิดกว้างกว่า ถูกดูดเข้าไปในโปรเจกต์ที่เข้มกว่าได้เสมอ แต่โค้ดที่เข้มกว่าจะลากทั้งโปรเจกต์ให้เข้มตาม**

---

## ตารางเช็คด่วน

แถว = license ของ dependency ที่คุณใช้ · คอลัมน์ = license ที่ผู้ใช้กำลังจะเลือก

| dependency เป็น | เลือก MIT/Apache ได้ไหม | เลือก MPL/LGPL ได้ไหม | เลือก GPL/AGPL ได้ไหม |
|---|---|---|---|
| MIT, BSD, ISC, Zlib, Unlicense, CC0 | ✅ | ✅ | ✅ |
| Apache-2.0 | ✅ | ✅ | ✅ GPL-3.0 · ⛔ GPL-2.0 |
| MPL-2.0 | ✅ (ไฟล์ MPL ยังต้องคง MPL) | ✅ | ✅ |
| LGPL-2.1 / LGPL-3.0 | ⚠️ ได้ถ้า dynamic link + ไม่แก้ตัว lib | ✅ | ✅ |
| EPL-2.0 | ✅ (ไฟล์ EPL ยังต้องคง EPL) | ✅ | ⚠️ ได้เฉพาะเมื่อ EPL นั้นเปิด secondary license ไว้ |
| GPL-2.0 | ⛔ | ⛔ | ✅ GPL-2.0 เท่านั้น (เว้นแต่ระบุ "or later") |
| GPL-3.0 | ⛔ | ⛔ | ✅ GPL-3.0 / AGPL-3.0 |
| AGPL-3.0 | ⛔ | ⛔ | ✅ AGPL-3.0 เท่านั้น |
| SSPL, BUSL, Elastic, PolyForm | ⛔ ห้ามใช้ใน open source ทุกกรณี | ⛔ | ⛔ |

`⛔` ไม่ได้แปลว่าโค้ดใช้ไม่ได้ แต่แปลว่า **ถ้าคุณแจกจ่ายงานที่รวมมันเข้าไป คุณต้องใช้ license ที่เข้มเท่ากันหรือมากกว่า**

## เคสที่เจอบ่อยและถ้อยคำที่ใช้อธิบาย

### เคส 1 — dependency เป็น GPL แต่ผู้ใช้อยากได้ MIT

พบบ่อยที่สุด ผู้ใช้มักไม่รู้เลยว่าตัวเองติดกับดักนี้

> "โปรเจกต์นี้ใช้ `{ชื่อ package}` ซึ่งเป็น GPL-3.0 อยู่ครับ
> license แบบนั้นมีเงื่อนไขว่า ถ้าใครเอาไปรวมกับโค้ดอื่นแล้วแจกออกไป โค้ดทั้งก้อนต้องเป็น GPL ตามไปด้วย
> แปลว่าตอนนี้คุณเลือก MIT ไม่ได้ครับ มี 3 ทางเลือก:
> 1. ใช้ GPL-3.0 ตามมัน — ง่ายที่สุด ไม่ต้องแก้อะไร
> 2. เปลี่ยนไปใช้ package อื่นที่ทำงานคล้ายกันแต่เป็น MIT
> 3. ถ้าโปรเจกต์นี้ไม่เคยแจกออกไปไหน ใช้ในองค์กรอย่างเดียว เงื่อนไขนี้ยังไม่ถูกกระตุ้น — แต่วันที่แจกออกไปจะต้องกลับมาแก้"

### เคส 2 — dependency เป็น Apache-2.0 แต่ผู้ใช้อยากได้ GPL-2.0

> "`Apache-2.0` กับ `GPL-2.0` เข้ากันไม่ได้ครับ เพราะ Apache มีเงื่อนไขเรื่องสิทธิบัตรที่ GPL-2.0 ถือว่าเป็นข้อจำกัดเพิ่มเติม
> ทางออกคือใช้ `GPL-3.0` แทน ซึ่งเขียนมาเพื่อรองรับกรณีนี้โดยเฉพาะ
> เว้นแต่คุณต้องเข้ากับ Linux kernel จริง ๆ ซึ่งกรณีนั้นต้องเปลี่ยน dependency แทน"

### เคส 3 — ผู้ใช้อยากได้ source-available แต่มี dependency เป็น copyleft

> "ตอนนี้โปรเจกต์ใช้ `{ชื่อ package}` ที่เป็น {GPL/AGPL} อยู่ ซึ่งบังคับให้ทั้งโปรเจกต์ต้องเป็น open source
> การเลือก BUSL หรือ Elastic License จะขัดกับเงื่อนไขของเขาโดยตรง — เท่ากับละเมิด license เขา
> ต้องถอด dependency ตัวนั้นออกก่อน หรือไปเจรจาขอ commercial license จากเจ้าของครับ"

นี่เป็นเคสที่ห้ามปล่อยผ่านเด็ดขาด เพราะเป็นการละเมิด license ของคนอื่น ไม่ใช่แค่เลือกไม่เหมาะ

### เคส 4 — dependency เป็น LGPL

ไม่ใช่ปัญหาในกรณีปกติ แต่มีเงื่อนไขติดมา:

> "`{ชื่อ package}` เป็น LGPL — ใช้กับ MIT ได้ครับ ตราบใดที่คุณไม่ได้แก้โค้ดของ library ตัวนั้น
> แต่ถ้าคุณ compile รวมเข้าไปในไฟล์เดียว (static link) จะมีเงื่อนไขเพิ่มว่าต้องทำให้ผู้ใช้เปลี่ยน library เป็นเวอร์ชันอื่นได้เอง
> ถ้าเป็นการเรียกใช้ปกติผ่าน package manager ไม่ต้องกังวลครับ"

### เคส 5 — ไม่มี dependency เลย

บอกสั้น ๆ แล้วไปต่อ ไม่ต้องอธิบายเรื่องที่ไม่เกี่ยวข้อง — "โปรเจกต์นี้ไม่มี dependency ภายนอก เลือก license ได้อิสระเต็มที่ครับ"

## วิธีตรวจ license ของ dependency

อ่าน manifest เพื่อดู direct dependency ก่อนเสมอ แล้วค่อยเลือกเครื่องมือตาม ecosystem
ถ้าเครื่องมือไม่มีติดตั้งอยู่ **อย่าไปติดตั้งอะไรลงเครื่องผู้ใช้** — ให้ถอยไปใช้วิธี registry API แทน

| Ecosystem | คำสั่งที่เร็วที่สุด |
|---|---|
| Node / npm | `npx --yes license-checker --summary` |
| Python | `uv run --with pip-licenses pip-licenses --format=markdown` |
| Rust | `cargo license` (ถ้ามี) หรืออ่าน `Cargo.toml` |
| Go | อ่าน `go.mod` แล้วเช็ค repo ต้นทาง |
| PHP | `composer licenses` |
| Java | อ่าน `pom.xml` / `build.gradle` |

**วิธีถอยที่ใช้ได้กับทุกภาษา** — อ่านชื่อ direct dependency จาก manifest แล้วถามจาก registry ทีละตัว:

```shell
# npm
xh -b GET https://registry.npmjs.org/{package}/latest | jq -r '.license'

# PyPI
xh -b GET https://pypi.org/pypi/{package}/json | jq -r '.info.license, .info.classifiers[]' | grep -i license

# GitHub repo ใด ๆ
gh api repos/{owner}/{repo} --jq '.license.spdx_id'
```

**สนใจเฉพาะตัวที่เป็นปัญหา** — ถ้าผลลัพธ์เป็น MIT / BSD / Apache / ISC ทั้งหมด ไม่ต้องรายงานรายตัว
บอกแค่ "ตรวจ dependency แล้ว เป็น permissive ทั้งหมด ไม่มีข้อจำกัด" แล้วเดินต่อ
รายงานเป็นรายตัวเฉพาะเมื่อเจอ GPL / AGPL / LGPL / MPL / EPL / SSPL / BUSL / Elastic / PolyForm หรือ **ไม่มีระบุ license เลย**

**dependency ที่ไม่ระบุ license** อันตรายกว่า copyleft — เพราะโดยค่าเริ่มต้นตามกฎหมายลิขสิทธิ์ "ไม่มี license" แปลว่า **ไม่อนุญาตให้ใช้เลย**
ต้องเตือนผู้ใช้ให้ไปถามเจ้าของ package หรือหาตัวแทน

## เมื่อไหร่ที่เงื่อนไข copyleft ยังไม่ถูกกระตุ้น

จุดที่คนเข้าใจผิดบ่อย: **เงื่อนไข GPL ส่วนใหญ่จะมีผลตอน "แจกจ่าย" (distribute) เท่านั้น**

| สถานการณ์ | copyleft มีผลไหม |
|---|---|
| ใช้ภายในองค์กร ไม่ส่งออกไปข้างนอก | ❌ ยังไม่มีผล |
| แจกไฟล์โปรแกรม / ปล่อยลง repo สาธารณะ / ขายเป็นสินค้า | ✅ มีผล |
| เอาไปรันเป็นเว็บให้คนอื่นใช้ ไม่ได้แจกไฟล์ | ❌ สำหรับ GPL · ✅ สำหรับ **AGPL** |

นี่คือเหตุผลที่ AGPL มีอยู่ และเป็นเหตุผลที่ผู้ใช้ที่ทำ SaaS ต้องตอบคำถาม Q4a ใน `interview.md` ให้ชัด

## เส้นแบ่งที่ต้องไม่ข้าม

skill นี้ช่วยเลือกและตั้งค่า license ได้ แต่**ไม่ใช่คำปรึกษาทางกฎหมาย**
ต้องบอกผู้ใช้ตรง ๆ ให้ไปหาทนายเมื่อเจอสถานการณ์เหล่านี้ แทนที่จะเดาให้:

- มีข้อพิพาทหรือมีคนอ้างว่าโค้ดถูกละเมิดอยู่แล้ว
- จะทำ dual licensing เชิงพาณิชย์จริงจัง (ขาย commercial license คู่กับตัวฟรี)
- ลิขสิทธิ์อาจเป็นของนายจ้าง มหาวิทยาลัย หรือแหล่งทุน
- โปรเจกต์เกี่ยวข้องกับสิทธิบัตรที่จดไว้แล้ว
- ต้องแก้ถ้อยคำใน license ต้นฉบับ (การแก้ทำให้มันไม่ใช่ license มาตรฐานอีกต่อไป และเครื่องมือตรวจสอบทั้งหลายจะอ่านไม่ออก)
